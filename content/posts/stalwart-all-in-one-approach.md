## Why Stalwart Stands Out

I first heard about [Stalwart](https://stalw.art/) at [FOSDEM 2025](https://fosdem.org/2025/), and properly met it at [FOSDEM 2026](https://fosdem.org/2026/), in the [Modern Email](https://fosdem.org/2026/schedule/track/modern-email/) devroom, during the talk
[Stalwart: Can Open Source do Gmail-scale Email?](https://fosdem.org/2026/schedule/event/FP8EFX-scaling-email/) by [Mauro De Gennaro](https://fosdem.org/2026/schedule/speaker/mauro_de_gennaro/). A bit of a clickbait title, I admit. But it got me started, and I learned much more afterwards from the documentation and the Discord community than from the talk itself.

The project describes itself like this:

> One server for your email, calendars, contacts and shared files, with spam and phishing protection built in. Every standard protocol your clients already speak (JMAP, IMAP, POP3, SMTP, CalDAV, CardDAV and WebDAV) supported natively.

As someone who has spent most of my career with Exchange Server - where "a mail server" means several roles, Active Directory, IIS, a database engine and a pile of prerequisites - I find a single Rust binary claiming to do all of that worth a closer look.

## Sovereignty

My main reason to look at this at all is sovereignty. I work (no surprise) for an international financial-market company that decided a few years ago to move its workplace services fully to the cloud, which in practice means Microsoft 365. Before that it was a Microsoft shop as well - I am not sure since which version, but I have found traces of Exchange 2007. I also saw some traces of Domino, although by the time I joined it was gone.

So the question I keep asking is simple: if one day we had to run mail outside a US hyperscaler, what would that look like today, with open-source software, and how far is it from what we know from Exchange? Stalwart is the first candidate I wanted to touch with my own hands rather than only read about. I do have one reservation: I would prefer a European vendor, and Stalwart Labs is a UK/US company. The server itself is open source, so this matters mostly for support and the Enterprise features.

## Protocol Support

### IMAP + JMAP + SMTP + CalDAV/CardDAV

All of these come from the same process and share one data store and one account directory:

- **SMTP** - inbound MTA on port 25 and authenticated submission (465), with SPF, DKIM, DMARC, ARC, MTA-STS and TLS reporting built in. DKIM signing keys are generated by the setup wizard, and the required DNS records can be published by Stalwart itself through the Cloudflare API.
- **IMAP** (and POP3, which I deliberately left closed) - the classic mailbox access every client understands.
- **JMAP** - the modern, JSON-over-HTTPS protocol. This is what Stalwart's own WebUI and CLI use, and what modern webmail clients talk to. It is also the most interesting part for me: think of it as what EWS/Graph should have been, but as an open standard.
- **ManageSieve** (4190) - server-side filtering rules with Sieve, the open-standard equivalent of inbox rules.
- **CalDAV / CardDAV / WebDAV** - calendars, contacts and files from the same server and the same accounts.

On top of that there is a built-in spam and phishing filter, an administration WebUI (`/admin`), a self-service account portal (`/account`) with 2FA and passkeys, and Stalwart can act as an OpenID Connect provider for other applications. What is *not* there, from an Exchange point of view: no MAPI, no EWS, no ActiveSync. Outlook connects as an IMAP client - Stalwart answers autodiscover/autoconfig to make that setup painless, but it is still IMAP.

## Installation and Basic Setup

My plan was the simplest possible configuration: all-in-one, single node, Stalwart's own account directory. This is not a production design - for the scenarios I have in mind as targets I would need HA, a separate identity layer and much more - but you have to start somewhere to get basic experience.

The lab ended up like this:

- **One VPS** - Rocky Linux 10.2, 2 vCPU, 4 GB RAM, static IPv4 with PTR, port 25 open both ways. Mail domain separate from server name, both DNS zones on Cloudflare.
- **Podman, rootful, with Quadlet units** - every container is a systemd unit, so `systemctl` and `journalctl` work as you would expect.
- **Traefik in front of everything** - it is the only thing with published ports. It terminates HTTPS for the WebUI and JMAP, and passes SMTP, IMAPS and ManageSieve through as raw TCP with the PROXY v2 header, so Stalwart still sees the real client address and does the mail TLS itself. Traefik also owns Let's Encrypt (DNS-01 on Cloudflare); a small certs-dumper container exports the certificate as PEM files for Stalwart, and a systemd timer asks Stalwart to reload it daily.
- **Stalwart v1 (1.1.1 at the time)** with the **internal directory** - accounts, argon2id password hashes, 2FA and passkeys all live inside Stalwart.
- **Host preparation with a local Ansible playbook** (ansible-core only), SSH by key for a dedicated admin account, root login off, `/admin` reachable only from my own address range, and Cockpit for the moments when I want a GUI on the host.

### PostgreSQL... for about one afternoon

My original idea was PostgreSQL behind every Stalwart store that supports it: one well-known engine to back up, monitor and restore, and a path towards a cluster later. I wrote it down, built it - and on the same day went back to the default, embedded **RocksDB**.

The reasons were pragmatic. Stalwart's documentation recommends RocksDB for a single server with the blob, search and in-memory stores left at *Default*; it is the configuration the tutorials use. It needs about 0.95 GB of disk per GB of mail against roughly 1.45 GB with PostgreSQL, and it removes a container, a network, a secret and a database server to patch. For a one-node lab, none of what PostgreSQL gives was actually needed.

The price is real, though, and worth stating clearly:

- **Single node only.** Only one process can open a RocksDB directory. Growing into a cluster means moving to PostgreSQL, MySQL or FoundationDB - and that is a data migration, not a setting.
- **Backups need a short stop.** A running RocksDB directory must not be copied file by file, so the nightly backup stops Stalwart for a few seconds, exports the volumes and starts it again (or you use atomic provider snapshots).
- **No SQL access** to the data. Inspection and export go through Stalwart itself.

### Identity: internal now, Keycloak maybe later

Identity is, for now, simply Stalwart's internal directory. I also looked at Keycloak as an OIDC identity provider, mostly for SSO, central user management and to learn Keycloak itself. On paper it works, but the consequences are significant: Stalwart becomes a resource server that only validates tokens, mail clients have to log in with OAuth (`OAUTHBEARER`/`XOAUTH2`), accounts appear only at the first sign-in, disabling a user in Keycloak does not disable the mailbox, and the built-in 2FA, passkeys and self-service password change are gone. Plus a JVM and another PostgreSQL on a 4 GB VPS. This stays a proposal until I test my actual mail clients against it in a lab.

### Extras

Because it was fun, I also added **Bulwark Lite** webmail, which Stalwart serves itself as an *Application* (no extra container - Stalwart downloads and unpacks the bundle), and a separate **root-fr JMAP webmail** container on its own subdomain, talking to Stalwart's `/jmap` directly from the browser. That one needed CORS for a single origin, which I did in Traefik rather than enabling Stalwart's permissive CORS.

## First Impressions vs Exchange Server

Here is what stayed with me.

### What feels good

- **One process, one data store, one place to look.** No roles, no Active Directory schema extension, no IIS, no .NET prerequisites, no CU that takes an hour to install. A container image tag and a volume - that is the server.
- **Configuration is data, not files.** Stalwart v1 keeps its configuration as objects in the data store, managed through the WebUI, the API or `stalwart-cli`. Only the data store connection lives in `config.json`. The CLI can `apply` declarative NDJSON plans with a `--dry-run` - which felt surprisingly familiar to someone who does everything in Exchange Management Shell anyway, except that the plan file can live in Git.
- **Mail authentication is first-class.** DKIM signing, DMARC, ARC, MTA-STS and TLS reporting out of the box. On-premises Exchange still has no native DKIM signing; you need a third-party agent or you route through EOP. Here, the wizard generated the keys and Stalwart published the DNS records through the Cloudflare API.
- **Spam filtering included.** No Edge Transport, no separate appliance, no EOP subscription.
- **Calendars and contacts over open protocols.** CalDAV and CardDAV instead of MAPI/EWS, which means any client on any platform.
- **Resource footprint.** The default memory limits add up to about 2.4 GiB, and everything - Traefik included - fits on a 4 GB VPS. Compare that with the RAM recommendations for a single Exchange Mailbox server.
- **The proxy story is clean.** Traefik in front, PROXY v2 for mail protocols, `X-Forwarded-For` for HTTP, and dedicated listeners that trust those headers only from the proxy's address. This is how you would want a load balancer in front of Exchange to work too.

### What bit me

Not everything was smooth. Things I actually hit on the server:

- **Configuration objects have semantics you need to learn.** Some plan entries are `upsert` and safe to re-run; the `Certificate` entry is a `create`, so applying the same plan twice gives you a duplicate. Coming from idempotent `Set-*` cmdlets, that needs attention.
- **JMAP vocabulary.** In JMAP a *Mailbox* is what everyone else calls a folder, so every JMAP command-line tool asking me for a "mailbox" means a folder, not an account. My Exchange brain keeps tripping over it.
- **Single node really means single node.** With RocksDB there is no DAG-like story. High availability is a different architecture (PostgreSQL/FoundationDB, S3 blobs, several Stalwart nodes), not a checkbox.
- **The rest of the stack has its own surprises.** Most of the remaining time went to non-Stalwart issues: SELinux (I run it permissive for now, while collecting the exceptions), a Podman secret that was not created on the first playbook run, and an upstream image bug in one of the optional containers.

### What I miss coming from Exchange

- **The Outlook experience.** No MAPI/EWS/ActiveSync means Outlook as an IMAP client, without the rich calendar sharing, delegation and free/busy that users take for granted. For clarity - I do not need Outlook itself. Rather, I need a real desktop client with full capabilities: an offline cache (like Outlook's Cached Exchange Mode) and a fully configurable interface.
- **A mature operational ecosystem.** There is a WebUI, an API and a CLI, but nothing like the depth of Exchange's cmdlets, message tracking, or the decades of community knowledge. Monitoring is still on my to-do list: nothing external yet, only what the Enterprise trial license provides.
- **A perimeter layer.** Built-in filtering is convenient in a lab, but in an enterprise I would not let internet traffic land directly on the server that holds user data. That means something Edge-like in front (an inbound relay or filtering gateway), or rethinking the whole approach.
- **Identity policies.** I still need to learn how Conditional Access-style policies work in viable Entra ID alternatives.
- **Hybrid and coexistence tooling.** There is no migration story comparable to Exchange hybrid; moving mailboxes means IMAP/JMAP-level tooling.
- **Compliance.** Stalwart sells it as Enterprise add-ons: [Compliance](https://www.stalw.art/compliance/) (retention policies, legal hold, eDiscovery search and export, journaling, audit trail) and, separately, [Lawful Interception](https://www.stalw.art/lawful-interception/) built into the mail server. Both need more investigation before I can compare them with Purview.

## Where I Am Now

The lab is running: mail flows through Traefik on ports 25, 465, 993 and 4190 with Let's Encrypt certificates, the WebUI and webmail answer, and the host is reproducible from an Ansible playbook plus a set of Quadlet units. Every decision is recorded as an ADR, which already paid off - the PostgreSQL decision is there, marked as superseded, with the reasons why.

Still to do before I would call it "tested": a real restore from the nightly backup, off-host backups (they currently stay on the same VPS - an accepted risk for a lab, not for anything else), external monitoring and verifying that the real client IP is logged on the proxy listeners. The Enterprise trial license is already imported, so the next step is to see what its monitoring and dashboards actually give me.

My first impression after a week: Stalwart is the most complete open-source "Exchange-shaped" server I have touched - a mail, calendar and contacts server in one process, with modern mail security built in, and a design that makes sense. It is not an Exchange replacement for an enterprise yet - mostly because of the client side and the operational ecosystem - but for the sovereignty question it is a very serious answer.
